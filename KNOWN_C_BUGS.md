# Known bugs and quirks in C LMDB 0.9.36 and what the Rust implementation does

Policy (see DESIGN.md): plain bugs are not reimplemented, but every deviation
must keep C and Rust processes interoperable on the same environment. Each
entry says whether it touches on-disk or lock-file state.

| # | Where in C | Behaviour | Rust behaviour | Interop impact |
|---|---|---|---|---|
| 1 | `mdb_load.c`, `flags = 0;` added for ITS#8662 | The first database's flags from the dump header (e.g. `dupsort=1`) are dropped. | `lmdb-tools` `mdb_load` keeps the header flags. | None: a tool bug; the file produced is simply what the user asked for. |
| 2 | `mdb_stat.c` | `mdb_stat -r` without `-a`/`-s`/`-f` exits 1 on success. | Rust `mdb_stat` exits 0. | None. |
| 3 | `mdb.c` key parsing in callers (mtest, tools) | Keys in the map are not NUL-terminated; reading past the last mapped page faults (SIGBUS). | Library never reads past a slice; callers get bounds-checked slices. | None. |
| 4 | `mdb.c` `mdb_cursor_next` (line 6027: `leaf = NODEPTR(mp, mc->mc_ki[mc->mc_top])` in the `MDB_DUPSORT` branch) | No `ki < NUMKEYS` check. After a failed `MDB_SET`/`MDB_SET_KEY` that searched the tree, the cursor sits at `ki == NUMKEYS`; `MDB_NEXT` then reads pointer slot `NUMKEYS` from the free space. A stale slot left by deletions can point at an old `F_DUPDATA` node, and C "succeeds" with a garbage key and a duplicate from the stale sub-cursor while staying past the end (`MDB_GET_CURRENT` then says `MDB_NOTFOUND`). | `lmdb::core` treats a position past the end as an item without duplicates and moves to the next item. | None: read-only API result. |
| 5 | `mdb.c` `mdb_cursor_count` (line 7914) | Checks `ki < NUMKEYS` only when `C_EOF` is set, then reads `NODEPTR(mp, ki)` unchecked; after a failed `MDB_SET` it usually reports a count of 1. | Returns `MDB_NOTFOUND` when the cursor is not on an item. | None: read-only API result. |
| 6 | `mdb.c` `mdb_cursor_open` + `mdb_xcursor_init0` | The sub-cursor's `mx_db` is never initialised (the cursor is `malloc`ed). If the main cursor is left on an `F_DUPDATA` node without `mdb_xcursor_init1` having run (e.g. a failed `MDB_SET` followed by `MDB_NEXT` or `MDB_PREV_DUP`), C searches a garbage root: `Assertion 'root > 1' failed in mdb_page_search()` in debug builds, undefined behaviour otherwise. | The sub-cursor starts as an empty tree: such a `MDB_PREV_DUP`/`MDB_NEXT_DUP` reports `MDB_NOTFOUND`, `MDB_NEXT`/`MDB_PREV` move to the neighbouring key. | None: no crash in Rust; read-only. |
| 7 | `mdb.c` comparators with mismatched sizes: `mdb_cmp_cint` reads `a->mv_size` bytes of *both* keys; `mdb_cmp_int`/`mdb_cmp_long` read 4/8 bytes; on branch pages `mdb_node_search` swaps `mdb_cmp_cint` for `mdb_cmp_long`/`mdb_cmp_int` by the size of the page's second key (line 5446). | With a search key longer than the stored integer keys, C reads the bytes that follow the stored key in the page (normally the node's data); shorter or odd-length search keys make it read before/after the caller's buffer. `lmdb.h` requires same-size integer keys, so this is misuse, but the result decides where a key would be inserted. | **Ported** where C is deterministic: the branch-page switch is reproduced and integer comparisons read the in-page bytes after a stored key (`Comparator::compare_in_page`). Bytes C would read outside any buffer are taken as zero. | Ported because sort order is shared state: a Rust writer must place a (misused) key where a C reader will look for it. |
| 8 | `mdb.c` `mdb_cursor_get(MDB_GET_MULTIPLE)` (line 6521) | If the sub-cursor is not initialised or at its end (e.g. the key has a single item), returns `MDB_SUCCESS` and leaves `data` untouched. | Returns success with an empty data slice. The C API can map that back to "untouched". | None. |
| 9 | `mtest*.c` with `MDB_FIXEDMAP` | A C-created `MDB_FIXEDMAP` environment records its map address in `mm_address`; a later C open with `MDB_FIXEDMAP` maps at that address and fails with `EBUSY` when ASLR placed something else there (seen on macOS: `mtest` cannot reopen its own `testdb`). | Rust ignores `MDB_FIXEDMAP` and writes `mm_address = 0` in a new environment (C would write the address). | None: address 0 means "anywhere" to C; C peers open Rust-created files with or without `MDB_FIXEDMAP`. |
| 10 | `mtest6.c` | Calls `mdb_dkey()`, which `liblmdb` only defines with `MDB_DEBUG`; does not build otherwise. | `lmdb/tests` builds it against a small shim that defines `mdb_dkey`. | None. |
