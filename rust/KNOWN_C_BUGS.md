# Known bugs and quirks in C LMDB 0.9.36 and what the Rust implementation does

Policy (see DESIGN.md): plain bugs are not reimplemented, but every deviation
must keep C and Rust processes interoperable on the same environment. Each
entry says whether it touches on-disk or lock-file state.

| # | Where in C | Behaviour | Rust behaviour | Interop impact |
|---|---|---|---|---|
| 1 | `mdb_load.c`, `flags = 0;` added for ITS#8662 | The first database's flags from the dump header (e.g. `dupsort=1`) are dropped. | `lmdb-tools` `mdb_load` keeps the header flags. | None: a tool bug; the file produced is simply what the user asked for. |
| 2 | `mdb_stat.c` | `mdb_stat -r` without `-a`/`-s`/`-f` exits 1 on success. | Rust `mdb_stat` exits 0. | None. |
| 3 | `mdb.c` key parsing in callers (mtest, tools) | Keys in the map are not NUL-terminated; reading past the last mapped page faults (SIGBUS). | Library never reads past a slice; callers get bounds-checked slices. | None. |
| 4 | `mdb.c` `mdb_cursor_next` (line 6027: `leaf = NODEPTR(mp, mc->mc_ki[mc->mc_top])` in the `MDB_DUPSORT` branch) | No `ki < NUMKEYS` check. After a failed `MDB_SET`/`MDB_SET_KEY` that searched the tree, the cursor sits at `ki == NUMKEYS`; `MDB_NEXT` then reads pointer slot `NUMKEYS` from the free space. A stale slot left by deletions can point at an old `F_DUPDATA` node, and C "succeeds" with a garbage key and a duplicate from the stale sub-cursor while staying past the end (`MDB_GET_CURRENT` then says `MDB_NOTFOUND`). | `lmdb::core` treats a position past the end as an item without duplicates and moves to the next item. | None: read-only API result. |
| 5 | `mdb.c` `mdb_cursor_count` (line 7914) | Checks `ki < NUMKEYS` only when `C_EOF` is set, then reads `NODEPTR(mp, ki)` unchecked; after a failed `MDB_SET` it usually reports a count of 1. | Returns `MDB_NOTFOUND` when the cursor is not on an item. | None: read-only API result. |
| 6 | `mdb.c` `mdb_cursor_open` + `mdb_xcursor_init0` | The sub-cursor's `mx_db` is never initialised (the cursor is `malloc`ed). If the main cursor is left on an `F_DUPDATA` node without `mdb_xcursor_init1` having run (e.g. a failed `MDB_SET` followed by `MDB_NEXT` or `MDB_PREV_DUP`), C searches a garbage root: `Assertion 'root > 1' failed in mdb_page_search()` in debug builds, undefined behaviour otherwise. | The sub-cursor starts as an empty tree: such a `MDB_PREV_DUP`/`MDB_NEXT_DUP` reports `MDB_NOTFOUND`, `MDB_NEXT`/`MDB_PREV` move to the neighbouring key. | None: no crash in Rust; read-only. |
| 7 | `mdb.c` comparators with mismatched sizes: `mdb_cmp_cint` reads `a->mv_size` bytes of *both* keys; `mdb_cmp_int`/`mdb_cmp_long` read 4/8 bytes; on branch pages `mdb_node_search` swaps `mdb_cmp_cint` for `mdb_cmp_long`/`mdb_cmp_int` by the size of the page's second key (line 5446). | With a search key longer than the stored integer keys, C reads the bytes that follow the stored key in the page (normally the node's data); shorter or odd-length search keys make it read before/after the caller's buffer. `lmdb.h` requires same-size integer keys, so this is misuse, but the result decides where a key would be inserted. | **Ported** where C is deterministic: the branch-page switch is reproduced and integer comparisons read the in-page bytes after a stored key (`Comparator::compare_in_page`). Bytes C would read outside any buffer are taken as zero. | Ported because sort order is shared state: a Rust writer must place a (misused) key where a C reader will look for it. |
| 8 | `mdb.c` `mdb_cursor_get(MDB_GET_MULTIPLE)` (line 6521) | If the sub-cursor is not initialised or at its end (e.g. the key has a single item), returns `MDB_SUCCESS` and leaves `data` untouched. | Returns success with an empty data slice. The C API can map that back to "untouched". | None. |
| 9 | `mtest*.c` with `MDB_FIXEDMAP` | A C-created `MDB_FIXEDMAP` environment records its map address in `mm_address`; a later C open with `MDB_FIXEDMAP` maps at that address and fails with `EBUSY` when ASLR placed something else there (seen on macOS: `mtest` cannot reopen its own `testdb`). | Rust ignores `MDB_FIXEDMAP` and writes `mm_address = 0` in a new environment (C would write the address). | None: address 0 means "anywhere" to C; C peers open Rust-created files with or without `MDB_FIXEDMAP`. |
| 10 | `mtest6.c` | Calls `mdb_dkey()`, which `liblmdb` only defines with `MDB_DEBUG`; does not build otherwise. | `lmdb/tests` builds it against a small shim that defines `mdb_dkey`. | None. |
| 11 | `mdb.c` `mdb_freelist_save` and `mdb_txn_commit` (`mdb_cursor_init` without tracking) + `mdb_page_split` (line 9038: `if (mc->mc_snum > snum) ptop++`) | The free-list and DB-record puts use a cursor that is not linked into `mt_cursors`. When a split of its leaf splits the parent recursively and that grows a new root, only tracked cursors get the new root pushed under them; the untracked cursor keeps a stack one level short. A later split through the same cursor in the same loop (e.g. re-putting the grown free-list record) inserts the separator into the wrong page. | Rust tracks these cursors. All fixup loops skip the operating cursor itself, so tracking only adds the adjustments nested splits/rebalances make, which C needs to keep the cursor valid. | None: same pages in the same places whenever C's result is consistent; avoids a corrupt tree in the rare nested-root-split case. |
| 12 | `mdb.c` `mdb_node_add` (`IS_LEAF2` branch, line 7496) via `mdb_cursor_put` on `MDB_DUPFIXED` | A duplicate whose size differs from the key's other duplicates is copied with `md_pad` bytes regardless: reading past a shorter item, truncating a longer one, and when a single item is converted to a sub-page the sub-page's item size is taken from the *new* item. | `MDB_BAD_VALSIZE` before anything is changed (also for `MDB_MULTIPLE`). | None: refuses what C would store corrupted. |
| 13 | `mdb.c` `_mdb_cursor_put` with `MDB_CURRENT` (line 6756, `goto current`/`more:`) | Only `C_INITIALIZED` is checked. On a cursor that is not on an item (past the end after a failed `MDB_SET`, …) C reads `NODEPTR(mp, NUMKEYS)` from the free space: debug builds assert in `mdb_node_del` (`indx < numkeys`), release builds return garbage results (`MDB_INCOMPATIBLE`, …) or overwrite page memory. | `MDB_NOTFOUND`, nothing changed. | None. |
| 14 | `mdb.c` sub-cursor record `mx_db` (`mdb_xcursor_init2` line 7786 called *before* the new duplicate is stored in `_mdb_cursor_put` line 7192; `mdb_cursor_set` clears only the flags; `_mdb_cursor_del` line 7289 uses `mx_db` as cached) | A cursor's cached duplicate record goes stale when another cursor adds or deletes duplicates of the same key, or after a failed `MDB_SET`/`MDB_GET_BOTH` (it still describes the previous key). C then: subtracts a wrong count for `MDB_NODUPDATA` deletes (`md_entries` off) and may `mdb_drop0` *another key's* sub-DB; deletes the whole key when the stale count reaches 0 although duplicates remain (data loss); writes the stale record into the node; returns another key's duplicates when moving; reports stale `mdb_cursor_count`s. | The record is re-read from the node before a sub-cursor delete and before `MDB_NODUPDATA`, and after a change it is copied to every other cursor on the same key. A sub-cursor on a sub-page finds it through its main cursor's current node, so it never reads another key's sub-page through a stale pointer (moving a cursor left by a failed `MDB_SET` over a key whose duplicates are in a sub-DB still walks the stale sub-DB, as in C, see #6). | Rust writes correct counts and data where C would corrupt them; files stay readable by C. `mdb_cursor_count` of other cursors is correct in Rust and stale in C (API only). |
| 15 | `mdb.c` `_mdb_cursor_put` with `MDB_CURRENT` on a duplicate in a sub-page (line 6960, `case MDB_CURRENT: ... goto put_sub`) | No room check: if the new item is longer and the sub-page is full, the sub-cursor's put calls `mdb_page_split` on the sub-page as if it were a page, allocating a branch and a leaf page that nothing references and losing the item. | As `lmdb.h` describes for `MDB_CURRENT` with another size: delete the current item, then insert the new one. | None: leaves a valid tree where C leaks pages. |
| 16 | `mdb.c` `_mdb_cursor_put` with `MDB_RESERVE` on `MDB_DUPSORT` | `lmdb.h` forbids it; C does not check: the reserved space is a duplicate that is compared and sorted while still uninitialised. | `EINVAL`. | None: API only. |
| 17 | `mdb.c` `_mdb_cursor_put` (line 6821, `P_LEAF2` for `(md_flags & (DUPSORT\|DUPFIXED)) == DUPFIXED`) on a database opened `MDB_DUPFIXED` without `MDB_DUPSORT` | The test is meant for DUPFIXED sub-DBs, but also hits user DBs with this (documented as invalid) flag combination: their pages become `P_LEAF2` with key size `md_pad == 0`, and `mdb_node_add` moves `mp_upper` past the end of the page. | `mdb_put` and `mdb_cursor_put` on such a DB fail with `MDB_INCOMPATIBLE` (the DB can be created and read, as in C). | None: refuses what C would corrupt. |
| 18 | `mdb.c` `mdb_cursor_next`/`mdb_cursor_prev` (moving onto a node without `F_DUPDATA` leaves the sub-cursor's `C_INITIALIZED`, index and `C_EOF` as they were) + `mdb_cursor_del0` fixup loop (line 8705: an "initialised" sub-cursor only gets `mc_pg[0] = NODEDATA(node)`) | A cursor that went from a key with duplicates onto a key without, and is then moved by a delete onto a key with duplicates, keeps the old key's sub-cursor position: `MDB_GET_CURRENT` reports `MDB_NOTFOUND` (or another than the first duplicate). | The cursor is on the first duplicate of the key it was moved to. | None: cursor state, API only. The differential test re-positions such a C cursor (`tests/write_differential.rs`, `stale_subcursors`). |
| 19 | `mdb.c` `mdb_dbis_update` (closes only `DB_NEW` handles on abort) and `mdb_dbi_open` (a name that is not open is looked up in the main DB) | (a) A handle a write transaction opened for a database that only exists because the same transaction (or a committed child) created it after the first handle was closed (`mdb_drop`, `mdb_dbi_close`) stays open after an abort: it names a database that does not exist, and `mdb_dbi_open` (even with `MDB_CREATE`) keeps returning it, its use failing. (b) Reopening, within a write transaction, the name of a database the transaction modified after its handle was closed reads the DB record from the main DB, which is only written back at commit: the transaction's changes to that database are lost and its new pages leak. | (a) An abort closes the handles that name a database which does not exist in the state it reverts to. (b) A name is reopened in the slot of the transaction's live view of it, keeping the view. | None for other processes (handles are per process); Rust writes the transaction's actual state where C would lose data and leak pages. |
| 20 | `mdb.c` `mdb_drop` with `del = 1` in a nested transaction (`mdb_dbi_close` at once) | The handle is closed for good even if the child then aborts; the parent's view of the database is then "changed" (`TXN_DBI_CHANGED`) and, if the parent had modified the database, its commit fails with `MDB_BAD_DBI`. | An aborting child reopens the handles it closed with `drop_db` (same slot, same comparators) for the parent. After a top-level abort the handle stays closed, as in C. | None: handles are per process. |
| 21 | `mdb.c` `mdb_drop` on the main DB (`mdb_drop0(mc, md_flags & MDB_DUPSORT)`, so `subs == 0`) | Emptying the main DB of an environment with named databases removes their records but frees none of their pages: they leak (`check-freelist` reports them, a compacting copy fails with `MDB_INCOMPATIBLE`). | **Ported.** | Ported because the free list is shared state: Rust leaves the file C would leave. |
| 22 | `mdb.c` `mdb_page_spill` (line 2052, case 2 of its own comment, and "can't spill twice") with `mdb_txn_begin` copying `mt_dirty_room` to a child | A nested transaction starts with its parent's remaining dirty room and cannot spill pages that an ancestor spilled (it unspills them when it writes them), so a child of a parent that has filled its dirty list may fail with `MDB_TXN_FULL`. | **Ported** (a limitation rather than a bug; C's comment suggests a preemptive spill at `mdb_txn_begin`, which would change which pages get spilled and so the free list). | Ported to keep the same spill decisions, hence the same free list, as C. |
| 23 | `mdb_load.c` header parsing | `format=print` stays in effect for every later database in the same input once seen. | The Rust `mdb_load` applies it only to the database whose header set it. | None: tool only. |
| 24 | `mdb_load.c` header parsing | Searches the whole 4 KiB line buffer for `=`, so a malformed header line can become a warning instead of the "unexpected format" error. | The Rust tool parses the line only. | None: tool only. |
| 25 | `mdb_load.c` line reading | Lines containing NUL bytes, and header lines over 4 KiB, are mangled. | Read whole. | None: tool only. |
| 26 | `mdb_load.c` `-a` | The "always greater" comparator stays installed on the main DB, so a named database later in the same input is loaded with the wrong order (C was seen to crash). | The default comparator is restored per database. | None: tool only; the produced file is what the user asked for. |
